# 并行处理、辅助照片 EXIF 与安卓互转

状态：2026-10-27 有限并行扫描／转换已接入初版；辅助照片 EXIF 和安卓直接互转待实现。并发算法、EXIF 字段细分与安卓支持矩阵是实施建议，需按以下验证门槛落地，不代表已经支持所有厂商格式。

关联：[照片队列分类与状态展示](照片队列分类与状态展示.md)、[当前格式范围](双向转换与移动布局.md)、[输出与共享规范](../design/输出位置与系统共享规范.md)。

## 1. 按设备性能并行扫描和处理文件

### 已确认目标

根据设备性能自动安排多个文件的扫描和转换，在保持原片只读、完整校验、覆盖保护与正确取消的前提下缩短批次耗时。首轮不要求用户理解或手动填写线程数。

### 实施前基线与约束

[ConversionService](../../gui/ConversionService.swift) 使用串行工作队列；[NativeBatch](../../native/BatchEngine.swift) 的扫描和批处理逐文件循环。[AndroidExport](../../native/AndroidExport.swift) 的部分媒体轨处理已有内部并行，文件级并发必须考虑这一层资源消耗。

解析与转换会读取完整文件、复制媒体数据；高清候选导出还会解码画面。只按 CPU 核心数同时打开大量照片可能增加内存和磁盘争用，因此「按性能」不能等同于「用满所有核心」。

### 建议的调度规则

- 扫描和转换分别设置有限并发；结合活动处理器数、内存预算、单文件大小与解码任务成本确定上限。具体公式与初始上限通过基准确定，不在需求中写死未经验证的数值。
- 一个任务内共享资源预算，媒体解码和内部轨道处理计入预算，避免多层并发叠加失控。低内存或高压力时减少新任务投放，最低可降为串行。
- 默认仍先扫描、后由用户启动转换；本需求不意味着扫描到一张就自动转换，也不默认扫描并转换整个图库。
- 按文件调度工作；仅派发有限数量在途任务，禁止一次创建与整个图库数量等同的重型任务。
- 最终队列与报告保持稳定的来源排序，实际完成可乱序。进度使用已完成数量，不再用文件序号假定完成顺序；当前阶段、处理中数量与总数准确。
- 扫描结果分批发布，尽早显示已识别项目；主线程聚合状态并限制刷新频率，不丢失单文件最终结果。
- 停止后不再派发新文件，在途任务进入原有取消和清理流程；等待在途任务收敛后才显示停止完成。已发布且校验通过的结果保留，暂存结果清理。
- 每个文件独享临时目录和媒体读写对象。共享统计、进度、结果集合与缓存必须有明确同步边界；不能直接对现有共享数组并行 append。
- 预先登记目标路径，同一目标不得由两个工作任务同时覆盖；来源去重和不同来源同名文件的目录区分规则继续生效。
- 覆盖询问集中串行呈现；可暂停新任务投放，其他已获授权的在途文件可继续。一次只显示一个询问，「应用于本次所有」覆盖后续未决选择；已有输出未获授权时不得开始替换。
- 停止、关闭窗口、权限失败均应解除待决询问，不能让后台线程永久等待；整批汇总、图库交付和自动共享只触发一次，并在所有在途任务完成收敛后执行。
- 并发度属于执行策略，不改变照片转换参数；仅改变并发度不应让有效续转结果失效。

### 验收

- 同一批次串行/并行的媒体内容、样本数量、PTS、封面、HDR 和结果数量一致；允许 UUID、任务时间及报告顺序之外的非媒体标识不同，不能要求每个新输出文件的完整哈希一致。
- 覆盖成功、覆盖失败、同名文件、单文件损坏、低内存、取消、等待询问时停止及多次启动不产生数据竞争、重复发布或漏报。
- UI 可持续响应；完成数单调递增且不超过总数，每项只计数一次。失败与静态跳过分类保持准确。
- 使用相同输入和设备，记录串行/自动并行的总耗时、峰值内存、最大在途数与设备信息，区分首次缓存与热缓存；SSD、小文件、大文件和候选解码批次分别比较。
- 在有并行收益的代表性负载上体现吞吐提升；I/O 受限等场景不承诺固定倍数。正式性能阈值在基线测试后确定，不以牺牲校验换速度。

## 2. 辅助轨照片继承主照片的基本 EXIF

### 已确认目标与范围

从辅助轨导出的照片写入与主照片一致、适用且可信的基本 EXIF，便于相册按拍摄信息组织。包括独立高清候选照片、被选作主封面的候选照片，以及候选照片作为 Live Photo 静态部分的输出。

「辅助轨照片」指解码辅助轨画面后输出的静态照片，不是独立 `.auxiliary.mov`；本需求不要求给 MOV 写入 EXIF。

### 当前实现

[CoverCandidateSession.writeJPEG](../../native/CoverCandidates.swift) 通过系统解码取得已经应用视频方向变换的像素，重新编码 JPEG，仅另写候选时间/index 的 XMP。它没有主照片元数据输入，需在调用链传递主照片的受控元数据。

不能把整个原 EXIF 或 MakerNote 块原样粘贴到新 JPEG。新图尺寸、方向、配对标识、缩略图和 HDR 数据可能与主照片不同。

### 建议的字段规则

| 字段 | 策略 |
| --- | --- |
| 原始拍摄日期、数字化日期、对应亚秒及时区 | 存在且可解释时继承；字段保持原有对应关系，不拼接不同来源日期 |
| 设备厂商/型号、镜头厂商/型号、作者/版权 | 原片存在时继承，不将目标安卓厂商写成拍摄设备 |
| GPS 及其必要参考字段 | 继承来源允许保留的有效位置，不恢复已被删除的位置；现有明确去位置策略优先 |
| 新图像素宽高、方向 | 按实际输出重建；已应用方向的像素使用正常方向，不能再复制主照片旋转值 |
| 色彩空间与配置 | 描述实际生成图像；不能盲拷主图 ICC、位深或 HDR 声明 |
| 曝光时间、ISO、光圈、闪光等拍摄参数 | 首轮不盲拷为辅助帧的实测参数；若需继承，须另行明确它们只表示来源主照片的拍摄背景 |
| MakerNote、序列号、原缩略图、Live Photo 配对标识及动态偏移 | 不作为基本 EXIF 整块复制；配对输出按现有规则生成自身标识，静态候选不携带无效配对声明 |
| 增益图与 HDR 元数据 | 不从主照片套用；辅助帧像素与主照片并非同一图像，沿用现有候选照片的实际 HDR 能力 |

本需求的默认理解是共享拍摄背景信息，不声称所有 EXIF 字段或辅助帧的逐帧曝光相同。拍摄日期按主照片继承；候选画面相对时间保留在既有候选 XMP/报告中，不用推算时间擅自改写原始拍摄日期。

元数据来源优先使用当前任务所选版本的主照片，不混用原片与编辑版。主照片缺失或字段无法解释时省略并记录原因，不用文件修改时间、导出时间或其他照片的信息补造。

输出后读回核对字段、尺寸和方向。存在的必需继承字段若未成功写入，不把该照片当作满足本需求的成功输出；按单个来源的现有原子发布规则保留旧结果并报告。可选坏字段允许省略，但须可追溯。

### 验收

- JPEG/HEIC 主照片来源、中文型号、带时区/亚秒日期、GPS 有/无、编辑版与缺少 EXIF 均覆盖。
- 每张候选保留自身索引与候选时间，符合白名单的共享字段与来源主照片一致。
- 横竖屏及旋转视频正确显示，新图尺寸准确，不发生二次旋转。
- 不残留失效 MakerNote、主照片缩略图、错误配对 ID 或不匹配增益图；候选 Live Photo 使用自身有效配对标识。
- 相册中的日期/位置效果须单独实测；读回成功不等于所有相册都按相同字段排序。

## 3. 安卓动态照片格式间互转

### 已确认目标

新增「安卓 → 安卓」任务方向，将已支持解析的安卓动态照片转换为用户选定的安卓目标封装。来源格式自动识别，用户选择目标格式；不要求先生成 Apple Live Photo 再二次转换。

这里的互转是动态照片封装互转，不扩展为任意静态图/视频拼接，也不默认包含所有照片编码与所有品牌私有 HDR 的互转。

### 当前能力与建议支持边界

来源可复用 [PhotoFormat](../../native/PhotoFormat.swift)，目标可复用 [AndroidExport.assemble](../../native/AndroidExport.swift)。但当前 `AndroidExport.convert` 从 Apple ContentIdentifier 配对取图像、视频和封面，不能直接当作安卓输入入口使用。

建议首轮输入限定为当前解析器能完整验证的单文件 JPEG、三星 HEIC；目标延续当前面向用户开放的范围：

| 输出载体 | 候选目标范围 | 限制 |
| --- | --- | --- |
| JPEG | Google/通用、小米、三星、华为、荣耀兼容、OPPO、vivo V2 | 每一来源/目标组合通过编码、时间和结构验证后才开放；不宣称全机型兼容 |
| HEIC | 三星 | 仅原始 HEIC 载荷可安全重封装时；不把已有底层分支误当作已开放支持 |

JPEG 不在首轮重新编码成 HEIC。HEIC 转 JPEG 可列为显式转码方案，需沿用已验证的 HDR 准备流程并清楚说明主图会重新编码；这部分作为建议范围，不能仅因文件后缀可写出而开放。

荣耀目标继续使用已确认的 Google 兼容路径，华为目标沿用其可验证的 LIVE_ 路径；不为了品牌命名强制套用已知有方向问题的尾标。源 EXIF 拍摄厂商/型号保留，目标格式另列，避免将三星拍摄设备改成小米设备。

### 转换与保真规则

- 直接解析静态载荷、主运动视频、音频、时间线和源封面，组装目标容器。允许必要的内部临时文件，不创建可见的中间 Apple 配对产物。
- 音视频原则上不重编码；需要重封装时核对逐样本内容、大小、PTS 和旋转变换。源辅助视频与私有结构能否写入目标必须逐项确认，不能默认丢弃。
- 源时间戳与源帧号都映射到真实视频样本，再写入目标要求的时间戳或帧号；有时间歧义、越界或不支持的时间线时明确失败，不用平均帧率或中点替代。
- JPEG 同编码转换优先保留主图和已有可解释增益图编码；重写动态声明、目录和偏移，不改变静态拍摄信息。
- 目标不支持源辅助轨、私有静态 HDR 或其他已识别载荷时，必须事先说明具体损失。首轮默认阻止有未获授权损失的转换；若后续提供明确降级或独立保留附件，应单独确认，不静默处理。
- 普通 SDR 不生成 HDR；未知私有 HDR 不伪装 Ultra HDR。主图格式发生显式变化时，展示重编码及 HDR 处理说明。
- 同格式/等价布局不代表结果已完成。只有原有任务和校验规则满足时才续转；不能把原文件存在直接计为已完成，也不静默覆盖输入。
- 校验成功后再原子发布；已有输出选择、可选报告、失败保护和停止行为与现有方向一致。报告记录来源识别格式、目标封装、媒体/时间校验、保留及不支持的载荷。

### UI 与交付

任务方向增加第三个方向「安卓 → 安卓」。具体采用三个分段还是统一任务选择菜单，待窄屏布局核对；不能以三项长文案挤掉当前操作。

来源摘要和队列分别展示真实来源格式与拍摄设备，设置区显示目标格式和适用载体；选择不适用组合时给出原因。输出为安卓完整单文件，沿用文件夹、直接系统共享、文件夹并共享；不承诺导回 Apple 图库可作为 Live Photo 播放。

分类沿用队列规范：确认静态的来源进入静态照片；损坏或不支持组合进入需检查，并区分来源损坏和目标不支持。设置变化后重新判断有效结果，不能继续复用不同目标的已完成状态。

### 验收

- 为每个开放组合建立来源/目标样本矩阵，包含真实原片与构造边界，分别记录本地结构验证和目标相册真机验证。
- 覆盖 JPEG→JPEG、允许的 HEIC→HEIC、显式允许的 HEIC→JPEG、同格式、多种来源混合批次、无音频、带音频、旋转、非零 PTS 和封面边界。
- 逐样本验证音视频；无需转码的图像/增益图编码保持；源文件哈希不变，输出无重复或冲突动态目录。
- 辅助轨或私有 HDR 不可表达时有明确阻断或事先获准的处理方案，不出现转换成功但隐性丢失。
- 失败回滚、覆盖、停止、续转、同名来源及系统共享载荷与新并行调度共同验证。
- 真机验证检查动态播放、声音、封面、旋转、拍摄日期和 HDR；本地解析通过不宣传为全部固件兼容。

## 4. 实施顺序与约束

建议先补辅助照片 EXIF（范围集中），再实现有限并发与稳定汇总，最后新增安卓直接互转并覆盖组合矩阵；若并发范围较大，可先实现并行扫描、再接文件转换。此顺序是工程建议，不改变三项需求优先级。

三项可分别交付。并行优化不得降低元数据和媒体校验要求；新方向不得把来源丢失的视频或未知 HDR 当作可以恢复的数据。

本次并行基础实现与限制见 [性能优化方案](../development/Swift引擎性能优化方案.md)。后续调试默认仅 Intel（x86_64），不生成 ARM、通用二进制、DMG 或 ZIP，除非用户另有明确要求。

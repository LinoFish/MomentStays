# 多品牌连拍处理调研

检索日期：2026-11-13。本文记录最初的来源格式调研和接入建议；后续已接入限定格式的 [Google 连拍实验支持](Google连拍实验支持.md)及[华为与三星连拍实验支持](华为与三星连拍实验支持.md)，尚未用真实跨品牌连拍样片验证。以下代码边界与优先级为最初调研时的快照。

结论：优先验证 Google/Pixel 的显式 XMP 标记，其次调查三星 SEF 连拍数据；华为可作为复用荣耀路线的样片验证对象。小米、OPPO、一加、realme、vivo、iQOO 本轮未找到足以直接实现自动分组的文件协议。不能把“品牌提供连拍功能”当作“已知其磁盘格式”。

## 当前项目边界

- [burst.rs](../../core/src/engine/burst.rs) 仅接受 Make 为 HONOR 或空值、扩展名为 JPEG、名称符合 `IMG_YYYYMMDD_HHMMSS_BURSTnnn[_COVER]` 的文件；帧号从 001 开始。同目录和来源组名共同限定分组，不按时间邻近猜测。
- 已有组计划、重复帧号检查、缺帧提示、代表帧选择、独立照片输出、原片归档和来源变化检测。`original_total_known=false` 表示只知道扫描到的成员，不证明原相机总帧数。
- 输出通过 Apple MakerNote `0x000b` 写组 UUID、`0x002b` 写逐帧 PhotoIdentifier；[pyjpeg.rs](../../core/src/pyjpeg.rs) 保留原 EXIF 字节，但活动 MakerNote 会指向新 Apple 标记。原厂商 MakerNote 字节仍可恢复，不等于第三方工具仍能按原目录读到它。
- [PhotoLibraryService.swift](../../apple/macos/Sources/PhotoLibraryService.swift) 在导入后回查成员、`burstIdentifier`、组成员集合及代表图。文件写标记成功与 Photos 实际成组是两项不同验收。

## 品牌与处理路径

| 品牌/来源 | 已检索到的证据 | 建议处理方式 | 尚缺的关键证据 |
| --- | --- | --- | --- |
| Apple/iPhone | MakerNote `BurstUUID`（0x000b）是连拍共享 ID；PhotoKit 公开组查询及代表图属性 | 作为标记读取和目标入库基准；已有 Apple 标记优先保留、验证 | 原生 JPEG/HEIC 连拍样片及不同系统版本回查 |
| Google/Pixel 多文件连拍 | ExifTool 定义 `XMP-GCamera:BurstID`、`BurstPrimary`，另有 `XMP-GCreations:CameraBurstID` | 优先实现只读探测；同命名空间、显式组 ID 形成候选组，代表标记与排序分别验证 | 各字段实际取值、相互关系、可靠帧序和完整组原片 |
| Pixel Top Shot / Motion Photos | Google 官方说明可从 Motion photos 选择其他时刻 | 保留实况容器路线；提取视频帧应作为单独能力评估 | 不可默认其候选帧等同于多张独立原始照片 |
| Samsung Galaxy | ExifTool 源码记录 SEFT `0x09e0` / `Burst_Shot_Info`、`0x09e1` / `BurstShot_Best_Photo_Info` | 增加 SEF 只读探测，验证数据载荷是否能提供共享组标识、最佳帧；保留全部尾部资源 | 标记载荷语义、帧序、机型/One UI 差异；出现名称本身不足以成组 |
| Huawei | 官方确认图库有连拍组和选帧操作；本轮未核实严格文件名协议 | 收集原始整组，检查能否新增 Huawei 文件名适配器 | 不能仅把荣耀 Make 白名单放宽就声明支持 |
| Xiaomi/Redmi/POCO | 官方确认 Timed burst；它是按间隔连续拍摄的模式 | 将定时连拍与高速连拍分别采样，检查文件名、EXIF/XMP 和完整目录 | MIUI/HyperOS 各版本组 ID、帧序、封面是否随原片导出保留 |
| OPPO/OnePlus/realme | 本轮未取得可复核的原片分组协议 | 按机型、系统、相机应用分别调查；无确定证据时保留独立照片 | ColorOS/OxygenOS/realme UI 不能因品牌关联而共用未经验证规则 |
| vivo/iQOO | vivo 官方手册确认有连拍操作，但未给出组元数据规范 | 获取完整组，检查原片字段与导出前后差异 | OriginOS/Funtouch OS、iQOO 的独立样片证据 |
| Sony 相机 | `ReleaseMode`、`SequenceNumber`，部分机型还有 `SequenceImageNumber` / `SequenceFileNumber` / `SequenceLength` | 可识别拍摄模式和帧序线索；缺少可信边界时仅展示候选，由用户确认 | 序号或模式不能独立证明组 ID；部分序列也涉及包围曝光等多帧模式 |
| Canon 相机 | `ContinuousDrive`、部分机型有效的 `SequenceNumber` | 按机型解释字段，不用连续文件编号直接拼组 | 多种 MakerNote 布局、边界证据；RAW burst 不在当前静态 JPEG 路线内 |
| Nikon 相机 | 部分 ShotInfo 布局包含 `SequenceNumber`，存在加密且依机型变化的结构 | 先做限定机型的只读提取 | 本轮未确认通用组 ID，不能承诺全品牌自动分组 |
| Panasonic/Lumix | `BurstMode`（0x002a）、`SequenceNumber`（0x002b），模式值还包括多种包围拍摄 | 先区分连拍、曝光/对焦/白平衡包围，再评估组边界 | 官方解码实现注明部分机型解释可能不同；序号不是唯一组 ID |

上述字段来源分别见下方链接；表中的接入方式和优先级是工程建议，不是厂商兼容性承诺。

## 关键来源与证据强度

1. **Apple：字段与公开 API。** [ExifTool Apple 源码](https://raw.githubusercontent.com/exiftool/exiftool/master/lib/Image/ExifTool/Apple.pm) 将 0x000b 定义为组共享 ID；[Apple burstIdentifier 文档](https://developer.apple.com/documentation/photos/phasset/burstidentifier) 说明同组资产共享标识，并提供组查询及代表图相关接口。公开读取接口不能证明任意改写文件都能成功成组。
2. **Google：字段已定义，样片语义仍待验证。** [ExifTool Google 源码](https://raw.githubusercontent.com/exiftool/exiftool/master/lib/Image/ExifTool/Google.pm) 定义上述三个 XMP 字段。`CameraBurstID` 和 `BurstID` 不应在未验证前混为同一字段；`BurstPrimary` 的文本取值也不应直接套用布尔解析。[Google Top Shot 帮助](https://support.google.com/pixelcamera/answer/9937175?hl=en-ID) 说明 Motion photos 选帧行为；这不构成多文件连拍存储规范。
3. **三星：存在解析线索，缺完整连拍规范。** [ExifTool Samsung 源码](https://raw.githubusercontent.com/exiftool/exiftool/master/lib/Image/ExifTool/Samsung.pm) 的 Trailer 表注释记录上述两类连拍条目，并说明 SEFT 尾部及部分 HEIC 的 `sefd` 数据位置。它们主要是观察记录，不是完整可用的组 ID/帧序解码器。APP5 的 `UniqueID` 语义也不明确，不能直接当连拍组 ID。
4. **华为：确认产品行为，未确认文件协议。** [Huawei Take Photos](https://consumer.huawei.com/en/support/content/en-us15919054/) 描述连拍及图库选帧，没有提供跨平台可用的文件分组规范。
5. **小米：确认定时连拍。** [Redmi 13C 官方说明](https://www.mi.com/global/support/faq/details/KA-503625/) 描述 Timed burst 的间隔拍摄。不能据此推断高速连拍命名规则，也不能从旧 MIUI 实现推断当前 HyperOS。
6. **vivo：确认拍摄能力。** [vivo 官方支持](https://www.vivo.com/en/support/questionList?categoryId=53693) 列出 Fast burst/连续拍摄相关条目；未给出文件组标识格式。
7. **相机：按机型解析 MakerNote。** [Sony 源码](https://raw.githubusercontent.com/exiftool/exiftool/master/lib/Image/ExifTool/Sony.pm)、[Canon 源码](https://raw.githubusercontent.com/exiftool/exiftool/master/lib/Image/ExifTool/Canon.pm)、[Nikon 源码](https://raw.githubusercontent.com/exiftool/exiftool/master/lib/Image/ExifTool/Nikon.pm)、[Panasonic 源码](https://raw.githubusercontent.com/exiftool/exiftool/master/lib/Image/ExifTool/Panasonic.pm)。字段同名不保证跨厂商甚至同厂商跨机型语义一致。

## 建议接入顺序

1. **Google/Pixel 显式 XMP 探测。** 先验证组 ID、代表标记和帧序；缺少帧序时不能凭组 ID 宣称原始顺序已恢复。旧式 `_BURST000_COVER` 是待验证线索，现有荣耀规则拒绝 000，不能直接共用。
2. **三星 SEF 探测与样片解码。** 先证明条目值在同组一致、跨组不同，并确认最佳帧含义。JPEG 头部增长后还要确认尾部索引/偏移有效，不能只验证尾部字节未变。
3. **华为最小扩展。** 通过整组样片确认文件名协议后，才增加有明确品牌边界的规则。
4. **其余手机品牌按样片扩展。** 自动分组证据不足时，可另行设计用户手动确认组和顺序的入口；记录为人工分组，不标成已恢复原机连拍关系。
5. **相机单列阶段。** 首阶段只评估静态 JPEG；RAW、HEIC/HEIF 多图序列及 RAW burst 容器需要独立读取与输出设计。

## 引擎扩展约束

- 将“来源证据提取”与已有组计划/转换分开，复用当前 batch、Stage、清单和图库回查。建议证据记录含 `vendor`、`evidence_kind`、`evidence_version`、`source_group`、`frame_index`、`source_cover`，未知值显式为空。
- 当前 `plans` 把缺失帧号按 0 排序，`filename` 也参与来源目录重扫。扩展不能只改首次扫描；必须同步组计划、来源范围重验、转换重验、清单和续转验证。
- 当前 `honor-burst` 来源格式及 `honor-burst-2` 实现修订绑定荣耀语义。新增来源需要明确的格式/证据版本契约，保留旧清单可验证性，不把其他品牌写成荣耀来源。
- 组边界采用品牌和来源命名空间，防止目录合并、同名文件或不同设备碰撞。拍摄时间、连号、视觉相似度只提供提示，不自动授权改写组关系。
- 新增品牌必须分别验收原图编码、EXIF/GPS、活动 MakerNote 的可读性、HDR/MPF/SEF 资源及输出恢复。完整归档原片与输出中仍能读取所有原厂字段是不同承诺。
- 无原始总数证据时保持“仅已观察成员”，缺帧不补齐；冲突代表标记、重复帧号和部分选择继续明确处理。实况组合不因识别出连拍标记而丢弃视频。

## 样片与验收清单

每个具体机型/系统/相机版本至少准备两组相邻拍摄的完整连拍（用于排除误合并），以及普通单拍、已删除中间帧、修改代表帧、重命名副本和图库导出副本。JPEG、HEIC、HDR、实况组合分别验证，不由一种推断其他组合。

先保留原始目录与文件名，通过只读工具记录字段：

```sh
exiftool -r -G1 -a -s -u -json /path/to/burst-originals > /tmp/burst-metadata.json
```

该命令只用于调研；未解码的私有资源还需结合容器结构检查，JSON 中没有字段不代表原片没有连拍信息。ExifTool 不作为本次新增运行时依赖。元数据报告可能包含 GPS、时间、设备信息与本地路径，按[本地样片与隐私](本地样片与隐私.md)仅保留在本地。

验收需同时覆盖：来源分组正确、顺序有据、代表帧语义明确、误合并被拒绝、输出资源完整、续转/恢复可用，以及 Apple Photos 导入后实际成组。此次只完成资料检索与代码边界核对，以上跨品牌样片验收尚未执行。

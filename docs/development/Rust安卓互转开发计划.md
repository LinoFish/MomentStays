# Rust 安卓动态照片互转开发计划

状态：开发计划，尚未实现。日期：2026-10-27。

目标：使用 Rust 实现安卓动态照片格式直接互转，依赖尽量跨平台，并将解析、封装、时间线和校验设计为后续其他转换方向可复用的核心。

本计划细化[安卓互转产品需求](../product/并行处理、辅助照片EXIF与安卓互转.md)第 3 节，不改变其保真与失败保护规则。当前支持范围以[格式说明](../product/双向转换与移动布局.md)为准；计划中的格式不代表已经支持。

## 1. 交付范围

### 第一阶段：JPEG 核心与命令行

- 输入：先实现现有解析逻辑覆盖的 Google/通用、小米、三星 JPEG 动态照片布局。
- 输出：Google/通用、小米、三星 JPEG；来源自动识别，用户指定目标封装。
- 路径：直接拆解原始静态载荷与 MP4，重建目标声明、偏移及尾标，不经过 Apple Live Photo。
- 保真：不重新编码静态图、视频或音频；保留适用的 EXIF、方向、ICC、已有可解释 Ultra HDR 增益图与参数。
- 首轮只接收可以原样携带 MP4 且时间线可完整验证的输入。需要重封装或转码的文件返回明确的不支持原因。
- 输出必须通过结构、媒体和封面校验；不满足条件的组合禁止发布结果。

### 第二阶段：现有 App 接入与品牌扩展

- 将安卓 → 安卓作为第三个任务方向接入 SwiftUI，沿用现有扫描、队列、有限并发、覆盖选择、停止、续转和交付机制。
- 逐项添加华为 LIVE_、荣耀兼容、OPPO、vivo V2 的已验证 JPEG 来源与目标。
- 荣耀目标采用现有 Google 兼容路径；华为目标使用已验证的 LIVE_ 路径。拍摄厂商/型号保留原值，不能改成目标品牌。
- 输出支持文件夹、系统共享、文件夹并共享。首轮不提供将输出作为 Live Photo 导入 Apple 图库的功能。
- 文件导入先验收；图库仅接入现有资源读取能提供完整安卓原件的路径，不推定所有图库资源仍保有动态载荷。

### 后续阶段

- 三星 HEIC → 三星 HEIC 原始编码重封装。
- 需要时增加跨平台 MP4 重封装能力。
- HEIC → JPEG、HDR 模型转换、辅助轨独立保留或显式降级，均单独评估并定义用户授权流程。
- 逐步实现 Apple 配对读取和 Live Photo 写入，再替换其他转换方向。

不在本次范围：独立安卓 App、任意图片与视频合成、视频重新编码、JPEG → HEIC、未知私有 HDR 转换、当前 Swift 引擎整体重写。

## 2. 当前代码与复用方式

- [PhotoFormat.swift](../../native/PhotoFormat.swift)：JPEG/XMP、厂商边界、封面与部分 MP4 元数据解析，可作为 Rust 行为参考。
- [AndroidExport.swift](../../native/AndroidExport.swift)：目标 XMP、SEF、LIVE_ 与容器组装可参考；现有入口依赖 Apple 配对，不能直接复用为安卓输入入口。
- [PhotoHEIF.swift](../../native/PhotoHEIF.swift)、[HEIFMetadata.swift](../../native/HEIFMetadata.swift)：HEIC 后续阶段参考。
- [ConversionService.swift](../../gui/ConversionService.swift)、[BatchEngine.swift](../../native/BatchEngine.swift)：保留任务调度、覆盖询问和发布边界，新方向通过适配器调用 Rust。
- [ConversionSettings.swift](../../gui/ConversionSettings.swift)：增加独立方向值和适用目标判断，逐个检查当前按两个方向写成的条件分支。

现有代码是移植参考和差异对照，不能作为唯一正确性依据。Rust 输出需同时满足格式约束、独立检查和真机验收。

## 3. Rust 模块与平台边界

拟新增 Cargo workspace，具体目录在实施时落地：

- `motion-core`：二进制边界检查、JPEG/XMP、厂商输入输出、媒体时间线、保留能力评估、转换和校验；不依赖 Apple 框架。
- `motion-cli`：提供 inspect、convert、verify，负责参数、文件流、暂存和命令行结果。
- `motion-ffi`：通过 C ABI 向 Swift 提供单文件能力；使用静态库接入，保持媒体解析与调度分离。

三个入口共用同一核心；CLI 与 App 不各写一套转换规则。核心只处理单个来源，App 继续拥有批量调度预算，避免 Rust 和 Swift 同时启动整批并发。

核心数据模型至少包括：

- `MotionAsset`：真实来源布局、静态资源、主运动轨、音频、辅助载荷、方向、HDR 描述与来源封面证据。
- `MediaTimeline`：有理数时间基准、DTS/PTS、样本范围、持续时间和轨道变换；不以浮点秒作为内部唯一依据。
- `TargetProfile`：目标布局、载体、封面表达方式、允许的载荷与边界限制。
- `ConversionPlan`：是否可转换、必要操作、保留项、潜在损失和阻断原因；在写文件前形成。
- `ValidationReport`：来源/结果摘要、逐轨媒体指纹、封面映射、图像与增益图校验、警告及引擎/报告版本。

接口职责顺序：inspect → plan → convert-to-staging → verify → publish。App 中最后一步由现有 Swift 发布机制负责，CLI 自行实现同等约束；同一任务只允许一个发布方。

C 接口约束：

- 使用不透明句柄和显式释放函数；输入借用期限、结果缓冲区所有权和线程约束写入头文件。
- 媒体通过受控文件或读取接口传递，不把整张照片编码为 JSON；JSON 仅用于小型版本化请求、结果和报告。
- 路径协议需明确 macOS/Linux 非 UTF-8 文件名和 Windows Unicode 路径的处理，禁止静默改写路径。
- 取消句柄允许从另一线程发起；进度回调不直接触碰 SwiftUI，终态只发一次，句柄销毁前等待任务收敛。
- Rust panic 不得跨 C ABI；可捕获的展开转换成内部错误。内存分配失败等进程级终止不承诺恢复。
- 错误码至少区分静态照片、来源损坏、不支持布局、封面歧义、目标无法保留载荷、I/O、取消和校验失败。

## 4. 依赖选择原则

1. 优先标准库与纯 Rust 库；按 XML 解析、哈希、序列化、错误处理、CLI 等实际需求引入，避免大框架和重复依赖。
2. JPEG 同编码互转不引入图像解码器；MP4 原样携带不要求安装 FFmpeg、ExifTool 或 Python。
3. MP4 时间线必须能检查样本表、PTS/DTS、旋转和适用的 edit list。第一阶段先做覆盖范围明确的解析；分片、加密、未知必要结构或复杂时间编辑在未验证前拒绝。
4. 不预先承诺某个媒体库满足所有要求。实施首日验证候选库的读写能力、维护状态、许可证、目标平台和传递依赖，再锁定版本。
5. 必须使用 C/C++ 媒体库时置于可选能力模块，记录构建与分发成本，不能让 JPEG 基础路径依赖平台私有框架。
6. 提交 Cargo.lock、声明最低 Rust 版本，检查许可证与已知漏洞；离线运行不下载组件。

## 5. 必须保持的行为

### 媒体、时间与元数据

- 原样携带 MP4 时核对整个 MP4 载荷哈希，并解析逐轨样本以验证源结构及封面。未来重封装路径核对每个压缩样本、数量、大小、DTS/PTS 和方向变换。
- 封面从明确的来源时间戳或帧号映射至实际呈现时间线，处理非零起点、变帧率和 B 帧；禁止平均帧率推算或默认视频中点。
- 目标写时间戳时使用目标单位并校验取整误差；写帧号时单独验证该布局的编号基准和呈现顺序。默认对齐容差沿用半帧规则。
- 清除或重建旧动态目录、偏移、厂商尾标，正确维护标准/Extended XMP 引用、JPEG MPF 与增益图关联，不能留下冲突声明。
- 静态图按图像编码数据与必要属性校验，而非要求修改元数据后的完整 JPEG 哈希不变；增益图编码与参数分别校验。
- 不把未知 APP 段、MakerNote 或辅助载荷直接当成可安全复制的数据。对含偏移引用或未知语义的结构，无法证明保留正确则阻断并说明。
- 原片只读；源数据在扫描、转换与发布间发生变化时拒绝复用或发布。校验与发布绑定同一来源快照，尽可能使用同一打开句柄并进行最终检查。

### 文件、停止与续转

- 每项任务独立暂存，输出与原片不得是同一文件，包括符号链接/硬链接别名；按当前产品规则阻止不安全输出目录。
- 覆盖授权仍由 Swift 集中处理，Rust 不弹窗；未获授权不能替换旧结果。
- 校验后才提交结果，优先使用目标文件系统内的暂存和原子替换；跨文件、跨目录提交不声称天然原子，沿用并验证现有恢复机制。
- 停止后不派发新文件，在途任务响应取消并清理，已成功发布结果保留；提交临界点与取消的先后次序明确记录，不能把成功发布误报为已撤销。
- 续转同时核对来源指纹、目标参数、引擎兼容版本和输出完整性，不能仅凭文件存在跳过。
- 报告至少包含来源布局、目标 profile、保留/阻断项、封面证据、校验结果和耗时；路径及个人元数据只在本地保存。

## 6. 阶段与工期

以下为单人、现有样片和可用 Rust 工具链齐备时的工程估算，不含等待设备或样片的时间；每阶段验收后再开放对应能力。

### M0：基线与可行性，0.5–1 天

- 清点真实/构造样片、来源布局和载荷，建立逐组合状态清单。
- 确认首轮 MP4 子集、封面语义、依赖和 C ABI 原型；检查现有并发/发布机制的接入点。
- 交付：支持矩阵初稿、最小构建、接口草案和风险结论。发现关键结构无法验证时先缩小公开范围并重估。

### M1：JPEG 核心与 CLI，2.5–4 天

- 完成 Google/小米/三星解析、JPEG/XMP/SEF 写入、MP4 时间线与封面映射。
- 完成原样载荷转换、独立读回校验、CLI 暂存与发布，补齐破损结构和保真测试。
- 交付：首版 CLI，以及首批实际通过的来源 → 目标组合。M0 + M1 累计约 3–5 天。

### M2：Swift 接入，2–3 天

- 静态库构建与 C ABI 适配，接入第三方向、扫描分类、参数快照和适用目标提示。
- 接入有限并发、停止、覆盖、续转、报告和系统共享；新方向不触发 Apple 配对入口。
- 交付：Intel macOS App 可完成首批格式互转；两个原有方向回归通过。

### M3：其余 JPEG 品牌与跨平台回归，2–4 天

- 扩展华为/荣耀、OPPO、vivo V2，按可验证布局逐组合开放。
- 验证未知载荷阻断、失败恢复、批量任务和隐私规则。
- macOS、Linux、Windows 的 Rust 核心与 CLI 执行构建及构造样例转换测试；缺少执行环境时记录为待验证，不能只凭跨编译声明运行通过。
- 交付：当前品牌范围内经过验证的 JPEG 子集和 App 集成；累计约 7–12 天。

### M4：HEIC 与复杂媒体，追加约 3–8 天，验证后重估

- 添加已验证三星 HEIC 直通；按需求补充必要重封装与辅助载荷能力。
- 真实手机相册检查播放、声音、封面、旋转、拍摄日期及 HDR。
- 含设备回归的扩展版预留累计约 2–4 周；无法获取设备的组合保留待验证状态。HEIC 转码和私有 HDR 模型转换不包含在该固定范围内。

## 7. 验证与开放门槛

实施时建立独立的支持矩阵，不能只记录“某品牌支持”。每行记录来源布局/版本、目标 profile、载体、媒体/HDR/辅助轨条件、构造测试、真实样片结构测试、目标机型/固件播放测试和开放状态。

- 首批 Google/小米/三星分别覆盖输入与输出，包括同格式，共 9 个方向组合；不能用一条 A → B 成功代替 B → A。
- 扩展品牌后对全部拟开放来源与目标做组合测试；对不支持的组合验证明确拒绝。荣耀与 Google 即使输出等价也保留用户选项及报告映射测试。
- 媒体边界：无音频/有音频、旋转、非零 PTS、变帧率、B 帧、封面首尾、时间戳冲突/缺失/越界、帧号边界、损坏样本表。
- 静态与元数据：普通 JPEG、Ultra HDR、Extended XMP、多辅助 JPEG、私有 HDR、EXIF 方向与日期/GPS、未知 MakerNote 偏移、截断及超大长度字段。
- 文件与调度：输入不变、同名来源、已有输出跳过/覆盖、磁盘满、权限失败、转换中源变更、取消、覆盖等待时停止、重复启动和失败恢复。
- FFI：缓冲区释放、重复/失效句柄保护、回调生命周期、并发取消与错误传递；解析器增加性质测试和模糊测试，重点检查越界及整数溢出。
- 对照：使用现有 Swift 解析器和独立结构检查交叉验证；差异需定位原因，不能复制旧实现错误使测试通过。
- 真机：本地结构通过与相册播放通过分别记录；只有结构验证的输出明确标注兼容性待验证，不宣传全机型支持。

每阶段结束运行相应 Rust 格式检查、静态检查、单元与集成测试。App 接入后运行现有 GUI/引擎、反向转换和工作区相关回归；只有新增失败或风险才扩大重复测试。

## 8. 构建、迁移与完成定义

- 保留现有 Swift 引擎处理安卓 → 苹果、苹果 → 安卓，新方向独立路由到 Rust；不支持时明确报错，不能静默切到旧引擎掩盖问题。
- App 构建脚本增加 Rust 静态库与头文件步骤，开发默认仅 Intel（x86_64）。Linux/Windows 验证仅针对 Rust 核心和 CLI，不要求迁移 SwiftUI。
- 不自动构建 ARM、通用 App、DMG 或 ZIP；安卓平台交叉编译与移动设备绑定留待后续平台任务。
- 后续替换顺序：共用解析/校验 → 苹果输入与安卓封装 → Live Photo 写入 → 图像/HDR/辅助帧处理。每一步独立验证后切换，平台图库与系统共享仍由 Swift 承担。
- 真实媒体、机型明细和完整报告遵循[本地样片与隐私](本地样片与隐私.md)，不提交个人样片。

本次 JPEG 集成版完成需同时满足：Rust 核心/CLI 可独立运行；App 新方向可用；所有公开组合有可追溯验收；损失与不支持情况明确阻断；覆盖、停止、续转和共享保持正确；原有两个方向回归通过；未验证的跨平台和真机能力明确列出。

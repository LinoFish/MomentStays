# Conversion interface and engine replacement

`ConversionEngine.swift` is the UI-facing boundary. Inject a `ConversionEngine`; never import native engine types into UI code. `convert` accepts local input URLs, an output directory and a target vendor, returns immediately, and delivers progress and exactly one completion on the main queue, in order, with no subsequent progress. A successful batch can contain failed/skipped items; inspect every item. A failed completion means the operation itself could not finish. Progress counts are advisory (including zero totals), not a percentage guarantee. Each implementation owns its background scheduling. The interface does not currently offer cancellation or Photos library access.

`inspect(input:cancellation:completion:)` accepts a readable local **original file**, not a thumbnail, rendered Photos image or video. It returns immediately and completes exactly once on the main queue. `.motion` requires positive recognition of an Android Motion Photo, `.staticImage` requires evidence of a complete static image without motion content, and `.unknown` covers unsupported, malformed or ambiguous content; never treat unknown or an error as motion. I/O and request errors are failures. Cancellation is cooperative: use a fresh `InspectionCancellation` per call, retain it and call `cancel()` when appropriate. If observed before completion, the operation reports `.cancelled`; cancelling after completion has no effect. Implementations may be unable to interrupt a read/parse in progress. The caller must keep the local original and any security scope alive through completion, and owns Photos authorization, resource export and cleanup. Do not treat an Apple Live Photo still alone as Android motion.

Inputs and output are file URLs; callers own security-scoped access, temporary file lifetimes and copying/importing results to Photos. Keep access valid until completion. Outputs are published directories, not necessarily individual media files. Implementations must not claim a successful conversion before publication; preserve per-item errors in `detail`. `report` is optional. Do not overwrite existing output without explicit product policy. A replacement should validate requests, deliver callbacks according to the contract, and preserve the distinction between operation errors and partial item failures. Implement the protocol in a separate type and inject it at the app composition root; the UI and model types should not need changing. Add implementation-specific integration and device tests in addition to the isolated mock tests.

## Existing engine investigation and adapter

`NativeConversionAdapter.swift` is an **opt-in iOS/macOS adapter**. Define `MOTIONLIVE_NATIVE_ENGINE` and `MOTIONLIVE_LIBRARY` and compile it in the same module as `native/*.swift`. On iOS also compile `ios/XMLCompat/XMLCompat.swift` and define `MOTIONLIVE_SWIFT_REFERENCE` to use the Swift parser rather than the Rust bridge. On macOS either use the same reference flag or link the existing Rust bridge/library. At the app composition root inject `NativeConversionAdapter()` as `ConversionEngine`; the UI must not depend on native types. It calls `NativeBatch.run` without changing conversion logic. Apple target selects `to-apple`; Android vendors select `to-android` with the requested vendor and the existing default JPEG options. The latter expects Apple Live Photo still/movie pairs, not arbitrary Android input; arbitrary Android-to-Android targeting is not provided by this interface adapter. The existing batch API has separate `android-to-android` behavior limited to a specific transfer, not a general vendor converter. Existing output is not implicitly overwritten; native resume/verification rules apply. Per-file status and detail come from the batch report; report files are enabled by native defaults. The adapter has not yet been validated with real-world native fixtures or on physical devices.

The reference inspection reads the file and uses `NativeBatch.scanFile`/`PhotoFormat.parse`: a parsed motion photo is motion, the native conservative `confirmedStatic` check is static, and all other parser failures become unknown; filesystem read failures are errors. Its cancellation is checked before work and at delivery but cannot interrupt parsing. This mapping has not been tested with Photos exports or device files.

The native code was originally written for macOS 12 and uses AVFoundation, ImageIO, CoreGraphics, CryptoKit, Darwin filesystem APIs, and optionally a Rust C bridge (`native/RustCore.h`). The iOS build uses XMLCompat and the Swift reference parser; it must still be tested with real Photos exports and physical devices. Audit filesystem and sandbox assumptions, security-scoped URLs and AVFoundation behavior. Keep any compatibility changes in a platform layer rather than changing the conversion algorithm. A future replacement can be injected without changing UI code.

## Standalone tests

From this directory run `swift test`. The Swift package compiles only the Foundation boundary and the conditional adapter (which is excluded unless explicitly enabled). Tests use a mock and exercise request, progress, result, inspection classifications, errors and cancellation without media, the Rust library, or an iOS app. For a synthetic adapter round trip on a Mac and an iOS simulator run `bash ios/Engine/BuildHelpers/run-adapter-check.sh` from the repository root. It requires Xcode, a bootable simulator and an arm64 Mac, creates its own fixture, then exercises inspection, Android-to-Apple and Apple-to-Google conversion through the adapter. The earlier standalone launcher did not complete on the builder. For a cross-platform synthetic byte comparison instead, run `bash ios/Engine/BuildHelpers/run-cross-platform-check.sh` from the repository root (requires Rust with the simulator target as well as Xcode). It uses the actual app integration test, preserves outputs, and compares identical inputs on Mac and iOS. Media hashes are printed; UUIDs, container timestamps, platform media writers and metadata can make whole-file bytes differ even when content is equivalent. Passing this synthetic check does not establish compatibility with vendor devices or all inputs.

## Observed synthetic cross-platform comparison (2026-10-30)

No full camera-origin Motion Photo or Live Photo pair was found in the repository; `core/tests/SOURCES.md` explicitly says the full public camera samples are not committed. The repository does contain base64-encoded test images in `core/tests/fixtures-pycli/` and a standalone playable sample video in `core/tests/fixtures-samples/real.mp4.b64`; the small motion-image fixtures have only 39-byte embedded MP4-like structures, not the full camera originals. Git LFS tooling was unavailable, and no LFS pointers were found in tracked text. On a generated 64×48 Google-style motion photo, `run-cross-platform-check.sh` passed its app-hosted simulator test (one test). The Mac used the Swift reference parser; iOS used the linked Rust parser and XMLCompat. Both used the identical original for Android-to-Apple; for Apple-to-Google both used the exact same Mac-generated paired still and movie. This tests only this synthetic SDR case, not physical devices, real-vendor media or all parser paths.

The Android-to-Apple outputs were **not byte-identical**: Mac/iOS JPEG sizes were 1,832/1,777 bytes (first difference offset 5), and MOV sizes were 3,508/3,508 (first difference offset 1,794). The JPEG first XMP APP1 segment sizes were 639/584 bytes; macOS serialized an XML declaration while XMLCompat did not, and namespace/attribute order differed. Their generated Live Photo identifiers also differed (UUIDs), and 27 bytes after the XMP segment differed. Manifests reported the same source hash, cover time (0.4 seconds), 30 frames, video packet hash and HDR status, but different identifiers and output hashes. A matching packet hash is not full output equivalence.

Apple-to-Google outputs were also **not byte-identical**: Mac/iOS JPEG sizes were 4,996/4,941 bytes (first difference offset 5), and XMP APP1 sizes were 1,184/1,129. The same XML declaration/order difference was observed. After the XMP segment, 12 bytes differed in the embedded movie, in repeated fields encoding 2026-10-30 02:14:07 and 02:16:54 UTC respectively, consistent with the separate remux creation/modification times. The manifests agreed on input still and paired-video hashes, cover timestamp/frame, compressed video packet hash, and SDR status; output hashes differed. These observations do not prove all metadata is equivalent or rule out other cross-platform differences.

## Sequential batch coordinator

`BatchConversionCoordinator` wraps any `ConversionEngine` without changing single-request behavior. Supply an ordered array of `BatchConversionRequest` values, each with a unique stable UUID and one complete `ConversionRequest` (including all files needed for that conversion). Reuse an ID to correlate updates/results, not to deduplicate inputs. Duplicate IDs fail the whole batch before starting; empty batches succeed. The caller retains input URLs, security scopes and output resources until the batch completion, including while cancellation is pending.

Callbacks are asynchronous on the main queue. Progress starts at zero and counts terminal request outcomes (including unscheduled cancellations), with a fixed total and monotonically increasing completed count; current engine progress is optional and advisory, not included as a fractional aggregate. A final progress update precedes completion. Results are ordered like requests: `.completed` preserves the entire engine result (whose items may themselves have failed or been skipped), `.failed` preserves an engine-level error, and `.cancelled` means never started. Failures do not prevent subsequent requests. An engine-level cancellation error is a `.failed` outcome, not an unscheduled cancellation.

Use a fresh `BatchConversionCancellation` per batch. Cancellation prevents scheduling further requests once observed; it cannot interrupt an in-flight conversion, whose actual result is retained. Cancellation races with scheduling, so a request already started finishes normally. Completion waits for that conversion and reports every remaining request as cancelled. The coordinator relies on the engine's main-queue, exactly-once completion and progress ordering contract.

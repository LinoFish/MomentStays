# momentstays-core (Rust, experimental)

Cross-platform port of the MomentStays Motion Photo container parser. It lives on
the `rust-core` branch and does **not** change the macOS app.

- Byte-level only: JPEG markers, MPF, XMP / Extended XMP, ISO BMFF boxes, Google
  cover-time descriptors, Huawei/Honor `LIVE_`, Samsung SEF (JPEG + HEIC `mpvd`), OPPO, vivo.
- No pixel decode or encode, no AVFoundation. Video and audio bytes are never touched.
- Error messages match `native/PhotoFormat.swift` verbatim so results can be diffed.

## Build and use

```bash
cd core
cargo build --release
./target/release/momentstays-core inspect photo.jpg            # JSON summary
./target/release/momentstays-core inspect -j 8 ~/Photos/       # whole folder in parallel, JSON Lines
./target/release/momentstays-core bench                        # synthetic throughput (or pass files)
./target/release/momentstays-core extract photo.jpg --still s.jpg --video v.mp4
cargo test --release
```

Works on macOS, Linux and Windows; Android builds are on the roadmap. Inputs are memory-mapped,
never copied whole.

## `momentstays` CLI: Python CLI replacement

A second binary, `momentstays`, ports the Python `motionlive` CLI (`scan` /
`convert` / `verify`) to Rust. It shares the crate but uses the Python CLI's
semantics, not the Swift engine's: only Google-marked Motion Photo JPEGs are
accepted, and error text follows the Python wording (e.g. `Not a marked Google
Motion Photo`, `Cannot locate embedded video from XMP`).

```bash
cargo build --release --bin momentstays
./target/release/momentstays scan ~/MotionPhotos          # JSON report, same shape as Python
./target/release/momentstays convert a.jpg -o out/        # Google JPEG -> Apple Live Photo
./target/release/momentstays verify out/*.json            # manifest + file hashes
```

Differences from the Python CLI, all deliberate:

- `convert` still needs the macOS Swift helper (`native/MotionLive.swift`,
  compiled on demand and cached in `.build/`): the QuickTime metadata step
  (content identifier, still-image-time mett track) and the legacy gain-map
  path run there, exactly like the Python version. The sample-copy MP4->MOV
  remux itself is now done in Rust (`remux::remux_to_mov`, ROADMAP item 9a);
  the CLI does not use it yet. On Linux `convert` fails at that step with
  `Conversion requires macOS 12 or later`; `scan` and `verify` work everywhere.
- `implementation_id` is the SHA-256 of the sorted `core/src/**/*.rs` sources
  plus `native/MotionLive.swift`. Python outputs are therefore never reported
  as `resumed` by this binary (they fail with "already exists and is not
  equivalent" instead); `verify_pair` itself only checks manifest structure
  and file hashes, so it accepts both versions' manifests.
- Cases where Python crashes or is undefined fail cleanly here instead:
  missing MPF index after Ultra HDR generation, missing `stops`/ICC in a
  native result, malformed XMP (details after the `Malformed XMP: ` prefix
  differ from CPython's), I/O errors (Rust wording, not `[Errno ...]`), and
  Unicode-digit integers (Python `int()` accepts them; this port does not).
  Underscore-separated integers (`1_000`) are accepted, as in Python.
- The Python package is not removed; whether it is deleted is a separate
  decision for the repo owner.

Parity tests: `core/tests/pycli.rs` compares parse results, `live_still` /
`ultra_from_apple` / `legacy_color_profile` byte output, `legacy_apple` stops
and gain bytes, and full `scan` JSON against fixtures generated from the
Python reference (`core/tests/fixtures-pycli/`, generated by
`/tmp/gen_pycli.py` during development; regenerate if the Python CLI changes).
Fixtures are stored base64-encoded (`.b64`) so they can go through the
text-only file push; the test decodes them, and the scan test decodes the
`.jpg` files into a temp dir before scanning.

## Android writers (`model`, JPEG path)

`model::MotionModel` is the neutral model: still JPEG bytes, MP4 bytes and a
cover (`Time(us)` or Huawei `Frame`), built from any file `format::parse`
understands. `model::write` writes it back out for Google, Samsung SEF,
Huawei LIVE_, OPPO or vivo JPEG, reusing the Swift `AndroidExport` layout
(XMP motion document, SEF directory, LIVE_ tail). Video bytes are copied,
never re-encoded; the still keeps its coding data and gain map (only XMP
segments are rewritten, MPF offsets repaired). Every write is validated by
parsing it back: video bytes, still coding hash and cover must match.

Refusals, not guesses: a Huawei target needs a frame cover and other targets
need a time cover; converting between the two needs the MP4 sample-table
reader (ROADMAP item 7) and is rejected for now. HEIC writers and MOV->MP4
remux are not implemented yet; see ROADMAP A1/A3/A5 and item 8/9b.

## MP4 -> MOV remux (`remux`, ROADMAP item 9a)

`remux::remux_to_mov(data, video_index)` rebuilds an MP4 as a QuickTime MOV
without re-encoding: the chosen video track plus all audio tracks are kept,
other tracks (Google mett, hint, text) are dropped. Sample bytes are copied
verbatim; stts/stsc/stsz/ctts/stss boxes are copied verbatim, stco/co64 is
rebuilt for the new mdat layout, mvhd/tkhd/mdhd are rebuilt (movie timescale
1_000_000, track timescales preserved), and the edit list is copied with
segment durations rescaled to the movie timescale, so the output playback
timeline matches the source. `remux::check_remux` validates a remux the way
Swift `movie()` does: per kept track, sample count, sizes, concatenated
sample hash and presentation times must match exactly.

Limits: negative presentation times are refused (no explicit edit-list
handling for them, same rule as Swift). The movie-level content identifier
(item 9b first half) is implemented: `remux_to_mov_with_identifier` writes
moov/udta/meta/ilst (UTF-8 `----` item), `read_content_identifier` reads it
back, and ffprobe independently reports the tag. The still-image-time mett
track (item 9b second half) is deliberately NOT written: its boxed sample
bytes are not pinned by any verifiable source and were not guessed — the
closing step is a Mac hex dump of Swift `movie()` output (see ROADMAP Needs
Mac check). Until then this output is a valid MOV with a content identifier
but not yet a Live Photo. Verified on Linux: 5 remux tests (synthetic
video+audio, mett-track drop, negative-PTS refusal, second video selection,
real ffmpeg H.264 file) plus ffprobe on the real-file output (pts/dts/sizes
identical to source, decodes cleanly), and 3 identifier tests.

## Parity

```bash
python3 scripts/check_rust_core.py                       # vs Python reference (any OS)
bash scripts/build_backend.sh                            # macOS: build the Swift test driver
python3 scripts/check_rust_core.py --swift .build/backend/native-tests --samples ~/MotionSamples
```

On macOS the script also compares `timestamp_us`, `ultra`, `coding_hash` and error
text with the Swift engine. Run it with real samples before relying on any module.

See [ROADMAP.md](ROADMAP.md) for what is ported and what is next.
